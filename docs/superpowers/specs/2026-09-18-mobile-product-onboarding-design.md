# Mobile product onboarding design

## Goal and scope

This slice lets a newly registered user create their one product, see the resulting owner state on `/dashboard`, and open a working public URL for an empty board. It follows the approved MVP behavior in `2026-08-17-feedback-board-mvp-design.md` and the mobile layout in `docs/mobile-design.dc.html`.

This pass implements the mobile layout. From `sm` up the onboarding form sits in the sign-in page's card, 440 pixels of content, because the sign-in page showed that the mobile layout stretched across a tablet looks wrong. Both pages render that card through `NarrowMain` in `src/components`. The desktop design draws onboarding in a 620-pixel card, but around a desktop composition: the address prefix in one row with the input, a hint under every field, and a footer with a note beside the button. The mobile composition stretched to 620 pixels is the look the sign-in card avoids, and with its padding and border that card is 694 pixels wide, wider than the viewport just above `sm`. The wider card comes back with the desktop composition, which belongs to later work.

The owner dashboard is not a card at any width. It lays out on the layout grid of the [layout grid design](2026-10-16-layout-grid-design.md), on the page's background as both designs draw it, under a header on the same grid. The heading, the notice, and the public address keep a 560-pixel measure, the address on the surface colour so that it stands off the background, and the empty state centres in the content area where the feedback will be listed. A name of 80 characters with no space in it breaks inside the heading, so it does not make a phone's page scroll sideways. The design's desktop composition of that page, with the board's name and the owner's actions in the bar, the counts, and the table, comes with owner management.

## User journey

The board is created on its own route, `/dashboard/new`, and `/dashboard` shows the board once it exists. A guest opening either reaches sign-in with that route as `returnTo`. Account creation without a `returnTo` ends on `/dashboard/new`: a person who signs up to vote arrives with a board in `returnTo`, so an account without one is most likely for a board of its own.

`/dashboard` for a user without a product shows "You don’t have a board yet" with a "Create your board" link to `/dashboard/new`, and `/dashboard/new` for a user who already owns one shows "You already have a board" with a "Go to your board" link to `/dashboard`. Both are centred on the page, as the not-found page is: they are messages, and a card would add nothing to them. Neither page redirects on what it reads: each streams behind its `loading.tsx`, and a redirect raised after streaming has started reaches the browser as a client-side navigation, the kind of redirect the router kept and replayed for the guest before the proxy took it over.

The design draws the form as a state of `/dashboard` and says there is no separate create route, so that an owner without a product never reaches an empty triage table. One route with both states had to share one frame and one loading state, and a provider above both to carry the success notice across the swap; the dashboard's own composition would have made each of those harder to share. Separate routes keep the design's aim: a signed-in user without a product meets an offer to create one, not an empty table.

The form collects product name, public address, and an optional description. The address is suggested from the name until the user edits it. Editing the address makes it independent of later name changes. The form shows the public URL prefix above the editable slug, following the mobile design. All controls are in one column and text fields are at least 48 pixels high. The submit button follows the last field, as in every form. The mobile design makes it sticky so that it stays visible while the description is typed, but iOS Safari, and Chrome on Android since version 108, shrink only the visual viewport for the keyboard, so a button stuck to the bottom of the layout viewport sits behind the keyboard anyway. A check on an iPhone with iOS 18 confirmed it and showed blank space below the stuck button once the page was scrolled. In the flow, the button sits above the keyboard whenever the form leaves room for it, and the keyboard's return key submits from either single-line field. The design's feedback sheet, a longer form, moves its buttons into the top bar instead.

A created board takes the owner to `/dashboard`, which shows the empty owner state: the product name as the page heading, the public URL with a copy-link control, and the empty state from design state 06. Copy link confirms with "Copied" for two seconds, as the settings design does, and the confirmation is announced. Beside it, "View public board" opens the board in a new tab, which the arrow the design gives it marks, so the dashboard stays as the owner left it. The link's accessible name says that it opens a new tab.

The success notice appears only after a successful creation, not on every later dashboard visit. The action redirects to `/dashboard?created=1`, replacing the form's entry in the history, so going back does not return to a form for a board that exists. The owner state's heading reads the parameter once, keeps it in state, and drops it from the address with `window.history.replaceState`, which Next.js keeps its router in step with. A reload or a copied link therefore says nothing. A probe against a production build showed the whole sequence: the action's response carries the dashboard, the address loses the parameter without another request, and the notice stays. The notice, "Your board is live", is a polite status that takes focus, since the submit button that had focus is gone and focus otherwise falls to the page body. It can be dismissed.

When another tab has created the account's board first, the form shows "You already have a board." in its banner with a "Go to your board" link to `/dashboard` under it, as it shows "Sign in again" under an ended session, and keeps what was typed.

The dashboard's layout carries a header with the app's name, Feedback Board, linking to `/`, and the sign-out button; the design's account menu is beyond the MVP. The layout does not check the session; the page does.

The URL prefix in the form and the public URL in the owner state use the deployment origin from `BETTER_AUTH_URL`, the origin `parseReturnTo` already compares against, so neither needs the request's headers.

## Field behavior

Product name is required, contains 2–80 characters after normalization, and collapses repeated whitespace. Description is optional, has a 500-character maximum, trims outer whitespace, and preserves internal line breaks. Slug is required, contains 3–48 characters, and uses lowercase Latin letters, digits, and hyphens.

Description normalization converts every CRLF and lone CR to LF before it trims and checks the length. A browser keeps LF in the field but sends each line break as CRLF: in Chromium, `FormData.get` returns `"a\nb"` while the request body carries `"a\r\nb"`. Without the conversion, a description the counter shows at 500 characters fails on the server by one character per line break, and CRLF reaches the database.

Slug input follows the MVP normalization order before validation: trim, lowercase, replace spaces and underscores with hyphens, remove unsupported characters, collapse repeated hyphens, and trim hyphens at both ends. The generated suggestion uses the same function, then keeps the first 48 characters and drops a hyphen the cut leaves at the end. A name may be 80 characters long, so without the cut the form would suggest an address it then rejects, under a field the user never touched. If a name cannot produce a slug of at least three characters, the user must enter a valid Latin slug. The manual-slug validation example in the visual mockup yields to this normalization rule: an input that normalizes to a valid slug succeeds.

Validation messages follow the design where it has them and keep its voice where it does not:

- an empty name: "Enter a product name";
- a name shorter than two characters: "Use at least 2 characters";
- any field over its maximum: "Remove N characters", where N is how far the normalized value exceeds it;
- an address that normalizes to nothing, such as one typed in Cyrillic: "Use Latin letters, numbers and hyphens";
- an address shorter than three characters: "Use at least 3 characters".

The auth forms keep "Use at most N characters" for now; bringing them in line with the design is a separate change.

The shared field pattern supports an optional character counter, which the form passes to `Field.Label` as `counter={{ count, max }}`. This form uses it for name, slug, and description. It counts what validation counts: the normalized value, with a line break as one character, so the form computes `count` from the value it already holds. The label renders the counter in the label row, as in the design, but beside the `<label>` element rather than inside it; inside it, the counter would become part of the field's accessible name and change with every keystroke. Past the maximum the count turns red and gains a wavy underline, and the maximum beside it stays as it was. The design colours the whole counter red, but that red is about as dark as the resting grey, a ratio of 1.45:1, and on 12-pixel text a change of hue alone is hard to see. An invalid field leaves the count alone: its error can have nothing to do with length, such as a taken address, and the field's border and message already show it. Authentication fields keep their existing presentation without counters. Their validation errors continue to explain length limits. The counter is presentation, not a substitute for validation.

The address field shows its prefix, the deployment host followed by `/p/`, inside the field's frame above the input, as the mobile design does. The prefix is a description of the field, so a screen reader announces it with the field.

The description needs a multi-line control. `Field.Control` fixes its height at 48 pixels, so `src/components/field` gains a textarea control with the same border, focus, and invalid styles. It follows the MVP rule of 16-pixel text below `md`, which stops iOS Safari from zooming into the focused field.

Each field runs its Zod schema on the client through Base UI's `validate`, in Base UI's default `onSubmit` mode: errors first appear when the form is submitted, then update as the user edits, as design state 09 shows. The counter supplies the immediate length feedback. A failing field blocks the request, because Base UI cancels the submit event and React does not run an action for a cancelled submit. The auth forms have no client validation, so this form introduces the pattern. The client uses the schemas the action uses, so the two cannot disagree.

The Server Action independently parses and normalizes every submitted value. Field errors appear below their fields, and Base UI's `Form` moves focus to the first invalid one. A taken slug appears under the address field. All three fields are controlled, because React resets a form after every action and an uncontrolled field comes back empty; controlled, every entered value survives any failed submit. An error with only a form-level message shows in the form's banner and moves focus there, since the form keeps every value and submitting again is the next step. The banner is `FormError` in `src/components`, formerly `AuthFormMessage` in `src/features/auth/ui`, which moves now that a second feature uses it. Like the other shared components it takes a plain value, the message, rather than the action error, and the form passes it a ref to move focus there. During submission, fields cannot be edited and a stable-width pending button prevents a second request.

## Server boundaries and data

The code follows the layers of the action slices design: in `src/entities/product`, `contracts.ts` holds the field bounds and the slug pattern, `schemas.ts` the Zod schemas, the normalization, and the slug suggestion, and `queries.server.ts` the reads; `src/features/create-product` holds the create-product Server Action and the form.

The bounds move into `contracts.ts` from `src/server/db/schema/products.ts`, which exports them today, and the database schema imports them from there. A client schema that imported them from the database module would pull `drizzle-orm/pg-core` and the table definition into the browser bundle. `getAuthBackTarget` reuses the slug pattern from `contracts.ts` instead of its own copy.

Both dashboard pages check the full session before reading owner data. The action validates input, performs its own full session check, writes the product, and redirects to the dashboard. It never trusts an owner ID from the form. The action's session check must not redirect: a protected action with no session returns `UNAUTHENTICATED`, while `requireSession` redirects to sign-in. `session.server.ts` therefore also exposes a reader that returns the session or `null`, which the auth-session design deferred until a caller needed one.

The existing uniqueness constraints on `products.owner_id` and `products.slug` enforce one product per user and globally unique public addresses, under concurrent requests too, so the action inserts without reading the owner's product first. The migration declares both inline, so PostgreSQL names them `products_owner_id_key` and `products_slug_key`. Drizzle wraps the driver's error in `DrizzleQueryError`, and the action reads the constraint name from its `cause` rather than matching message text. `products_owner_id_key` maps to a form-level `CONFLICT`, "You already have a board.", which the form answers with its link to the dashboard. `products_slug_key` maps to a field-level `CONFLICT` with the design's wording, "This slug is already taken. Choose another one." Missing authentication returns `UNAUTHENTICATED` with "Your session has ended. Sign in again to create your board."

A second product whose slug is also taken violates both constraints, and PostgreSQL reports the owner's, because it checks unique indexes in the order they were created. PostgreSQL does not document that order, so a database test pins it. A read before the insert would make the message independent of the order, but it would cost a query on every creation and change nothing a test can observe today.

`proxy.ts` sends a guest to sign in only for page requests, which are GET requests. A Server Action is a POST to the route that uses it, as Next.js documents for Server Functions, and the proxy used to redirect it too. A probe against a production build showed what that does to the form: the browser repeats the POST to `/sign-in` without the action's header, the client receives a page instead of an action result, and it shows the route error page with everything typed gone. With non-GET requests passing through, the action answers for itself with `UNAUTHENTICATED`, the form keeps its values, and a link under the banner leads to sign-in with `returnTo=/dashboard/new`. The proxy filters on the method rather than on a `next-action` header in its matcher: a native submit carries the action in its body, and Next.js does not document the header. Without JavaScript and without a session cookie the action still runs, and the page's own redirect then answers the POST with a 307 that the browser repeats to `/sign-in`, ending in a 500. That case waits for sign-in to work without JavaScript, which it does not today.

Both dashboard pages stream behind their `loading.tsx`, which replaces `instant = false`: the MVP specification lets no route ship with it, and the guest redirect that motivated it now happens in `proxy.ts` before anything renders. A cookie that outlives its session still meets the redirect mid-render, as `proxy.ts` describes. `/dashboard/new` loads with the form's skeleton. `/dashboard` loads with the owner state's, since most visits there come after the board exists; like the board's, it stands in for a sample board's name and address. Without JavaScript the skeleton stays, as it already does on `/sign-in`, so the form cannot be reached without it either.

An unexpected failure while creating returns `UNEXPECTED` through `toUnexpectedActionError`, after `unstable_rethrow`, so the form stays on screen with what was typed and shows the neutral message in its banner. Reads keep the route error boundary: a failed owner read on `/dashboard` or product read on the public board reaches `src/app/error.tsx`.

## Minimal public board

`/p/[productSlug]` renders the board as the design draws it, cut to what works today. The bar at the top carries the product's name followed by "feedback". The design puts a sign-in control on the bar's right, which waits until something on the board needs a session. Below the bar come the heading "What should we build next?", the description if the owner wrote one, with the line breaks they typed, and the first-feedback empty state from design state 04, "No feedback yet", without its Add feedback action. The design's tabs, filters, and sort have nothing to act on yet and are left out as well. Below `sm` the heading and description sit on the surface and the empty state on the page's background, as in the mobile design; from `sm` both sit on the background, with the desktop design's larger heading and margins. A name of 80 characters with no space in it is cut short in the bar and breaks inside the empty state's sentence, and a long link in the description breaks too, so neither makes a phone's page scroll sideways. The document title is the product name, set through `generateMetadata`. This small public page makes the URL from onboarding truthful.

The page and its metadata both read the product through `getProductBySlug` in `src/entities/product/queries.server.ts`. React's `cache` wraps it, so a request makes one query; a probe against a production build confirmed it. A value that is not a slug exactly as one is stored returns `null` without a query. `isProductSlug` checks the pattern and the length bounds and does not normalize, since `/p/Orbit-CLI` is not the address the owner chose. The table holds every stored slug to the same rules, and a database test checks values `isProductSlug` rejects against the table too.

Either `null` calls `notFound()`, which renders the root `src/app/not-found.tsx`. Its copy is design state 03, the state the design uses for an unknown slug, so the route needs no not-found file of its own, and the title becomes "Page not found". The status is 200, not 404. The page reads its params inside the Suspense boundary its `loading.tsx` creates, as `/sign-in` and `/dashboard` do, so the shell has already streamed when `notFound()` runs; Next.js keeps the 200 and adds a `noindex` tag (`not-found.md`, "Calling `notFound()` after streaming has started"). A real 404 would need the lookup in `proxy.ts`, a database query before every board request, which this slice does not add.

The loading state draws the board's parts with `SkeletonText`. The heading and the empty state's title are known. The product's name and description are not, and the skeletons design left the choice between a toned bar and a sample to the first skeleton that needs one: the board's skeleton uses a sample board, a short name and a two-sentence description. A sample wraps like real text at every width, so the geometry stories can compare the board rendered with the sample against its loading state, at a phone's width and on a tablet. A board with a longer, shorter, or missing description moves its empty state when it arrives. The board has no controls to line up, so `expectSkeletonGeometry` compares it on its height alone and no longer requires a control. `EmptyState` gains a skeleton beside it.

The board has no error boundary of its own, so a failed read reaches `src/app/error.tsx`. Design state 02 replaces only the region that failed and offers "Go to the board", which assumes a board around that region. Here the product read is the whole page, so there is nothing to keep, and the link would lead back to the read that just failed, which Retry already repeats. The full state belongs with the feedback list, once the board's bar and intro can stay while the list fails.

The public product read is independent of the viewer and remains uncached in this slice. The following public-board slice can add the MVP product cache contract after its reads and mutations are tested. When it does, creating a product must expire `product-slug:{slug}` with `updateTag()`: a visit to a slug before anyone claims it caches a not-found result, which would otherwise outlive the creation. Session and owner reads stay request-bound.

## Verification

Vitest covers name, description, and slug normalization, field boundaries, the slug suggestion's cut at 48 characters, conflict mapping, and authorization. The description boundary includes a 500-character value with CRLF line breaks.

Database integration tests verify one product per owner and one owner per slug, including concurrent creation attempts. They call the create-product action against the database, with only the session reader and `redirect()` mocked, so the constraint mapping and the owner taken from the session are tested as they run. They also read a product by its slug, find nothing for a slug no product has, and check that a value that is not a slug is answered without a query.

The repository had no database tests before this slice. Vitest had a `unit` project and a `storybook` project, and the CI job that runs them states that they need no database and no environment variables, and that a test needing a service belongs to another suite. The first pull request therefore adds a third Vitest project, `db`, that collects `*.db.test.ts` files, which the other two exclude. `pnpm test` keeps running only `unit` and `storybook`; a new `pnpm test:db` runs `db`, and `pnpm verify` runs it before the end-to-end suite. In CI it runs in the end-to-end job, which already provides PostgreSQL and the test environment.

The `db` project loads the test environment the way Playwright does and refuses any database other than `feedback_board_test`, then applies the committed migrations in its global setup. The guard and the migration step move out of `e2e/` into a module both suites import, so neither keeps its own copy. Like the end-to-end suite, these tests never reset the database. Each test inserts its own users directly into `users` and uses its own slugs, so the tests do not depend on order or on what earlier runs left behind.

Playwright extends the existing isolated test setup with registration, mobile create-board interaction, return to the owner dashboard without the notice's parameter in the address, and opening the empty public board from the owner state's link. It also checks that a taken slug leaves the other form values intact, that a second tab's form points to the board the first tab created, and that `/dashboard/new` points an owner to the board they have. For an unknown slug and for a value that is not a slug it asserts the not-found heading, the `noindex` tag, and the title, not the 404 status that `e2e/not-found.e2e.ts` asserts for an unmatched URL.

Each pull request is complete when `pnpm verify` and `pnpm build-storybook` pass. The slice is complete when the journey works at mobile widths, labels and errors are accessible, and the pending state prevents duplicate submission.

## Delivery

1. **Product domain.** `contracts.ts`, `schemas.ts` with the normalization and the slug suggestion, the create-product action, the nullable session reader, the database test project, and the database tests. Nothing renders yet.
2. **Form parts.** `FormError`, `Field.Description`, the counter on `Field.Label`, and the textarea control, each with stories. The auth forms move to `FormError`; nothing else renders differently yet.
3. **Dashboard.** The proxy change, the dashboard layout and its loading state, `queries.server.ts` with the owner's product, the onboarding form, the owner state with the public URL and copy link, the success notice, and Playwright coverage for creating a board, a taken slug, and a submit without a session.
4. **Public board.** `getProductBySlug`, `/p/[productSlug]` with its loading state, the owner state's link to it, and the Playwright journey extended to opening the empty board and to an unknown slug.
5. **Creation route.** `/dashboard/new` with the form and its loading state, the action's redirect with the notice's parameter, the two states for the wrong page, the owner state's loading state, and account creation's new default. `CreateProductProvider` goes, and the form owns its action state again.
6. **Owner layout.** The layout grid, and on it the owner state and its loading state, the two messages, the not-found and error pages, the dashboard's header, and the public board.
